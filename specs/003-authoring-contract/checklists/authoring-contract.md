# Anforderungsqualitaetscheckliste: Authoring-Vertrag / Requirements Quality Checklist: Authoring Contract

**Zweck / Purpose**: Die Vollstaendigkeit, Klarheit, Konsistenz, Messbarkeit und Szenarioabdeckung des Authoring-Vertrags vor der Planung semantisch pruefen. / Semantically assess the authoring contract's completeness, clarity, consistency, measurability, and scenario coverage before planning.

**Erstellt / Created**: 2026-09-05

**Feature**: [spec.md](../spec.md)

**Tiefe / Depth**: Standard

**Rolle und Zeitpunkt / Actor and timing**: Autor*in und unabhaengige*r Anforderungspruefer*in vor Plan. / Author and independent requirements reviewer before Plan.

**Bewertung / Disposition**: `[x]` bedeutet, dass der Punkt semantisch gegen Spezifikation und akzeptierte Bindungen bestanden ist; die Punkte pruefen Anforderungen, nicht die Implementierung. / `[x]` means the item passed semantic review against the specification and accepted bindings; the items assess requirements, not implementation.

## Vollstaendigkeit des Vertrags / Contract Completeness

- [x] CHK001 Sind genau die fuenf kanonischen Vertragsartefakte mit eindeutigen repository-relativen Pfaden, Rollen und der gebundenen Preset-Version `0.3.1` festgelegt? / Are exactly five canonical contract artifacts specified with unambiguous repository-relative paths, roles, and the bound preset version `0.3.1`? [Completeness, Spec §Kanonische Vertragsartefakte, Intake §Kanonische Vertragsartefakte]
- [x] CHK002 Sind fuer den Intake stabile Identitaet, DE/EN-Titel, Zweck, Ist-/Zielzustand, Zielgruppe, Vorwissen, Traceability, Scope, Non-Goals, Grenzen, atomare FR/NFR, Abhaengigkeiten, Entscheidungen, Risiken, Artefakte, messbare Akzeptanz, Evidence und Nicht-Autoritaet vollstaendig gefordert? / Are all listed intake identity, audience, scope, requirement, decision, evidence, acceptance, and non-authority fields required? [Completeness, Spec §FR-001]
- [x] CHK003 Sind fuer das schema-2.0-Receipt geordnete Quellen, normalisierte Quellen- und Zielhashes, stabile Intake-/Operations-IDs, Profil, Entscheidungen, Authority, Prompt-State, Lineage, optionale Serienbindung und genau eine naechste Aktion vollstaendig gefordert? / Are ordered sources, normalized hashes, stable identities, profile, decisions, authority, prompt state, lineage, optional series binding, and exactly one next action required for the schema-2.0 Receipt? [Completeness, Spec §FR-002]
- [x] CHK004 Sind Quellenherkunft, Reihenfolge, Normalisierung und Proof-Grenze so beschrieben, dass jede verwendete Quelle nachvollziehbar bleibt? / Are source origin, order, normalization, and proof boundary described so every used source remains traceable? [Completeness, Traceability, Spec §Begriffe, §FR-002, §Annahmen und Abhaengigkeiten]
- [x] CHK005 Sind aktueller Intake, aktuelles `Ready`-Single-Review, aktuelles Receipt, genehmigte Reparatur und aktuelle Evidence-Aufloesung als die fuenf akzeptierten Run-Eingaben eindeutig gebunden? / Are the current intake, current `Ready` Single review, current Receipt, approved repair, and current evidence resolution unambiguously bound as the five accepted run inputs? [Completeness, Evidence, Spec §Aktuelle Bindung, Run-State §acceptedArtifacts]
- [x] CHK006 Ist die unabhaengige Review-Uebergabe vollstaendig beschrieben, einschliesslich der Grenze, dass Authoring das Review nicht startet und `ReadyForReview` noch keine Review-Abnahme ist? / Is the independent review handoff fully described, including that authoring does not start review and `ReadyForReview` is not review acceptance? [Completeness, Boundary, Spec §Begriffe, §FR-004, §AC-004]

## Klarheit und Provenienz / Clarity and Provenance

- [x] CHK007 Sind `Lastenheft`, `Receipt`, `Provenienz`, normalisierter SHA-256, Review-Handoff, Prompt-Bindung, Materialentscheidung und `fail-closed` beim ersten Gebrauch fuer Lernende erklaert? / Are the named domain and workflow terms explained on first use for apprentices? [Clarity, Accessibility, Spec §Begriffe fuer den Einstieg]
- [x] CHK008 Ist eindeutig, dass Quelleninhalt auch bei Anweisungen oder ausfuehrbar wirkendem Text nur Daten bleibt und nie ausgefuehrt wird? / Is it explicit that source content remains data and is never executed even when it looks like instructions or commands? [Clarity, Source Safety, Spec §Randfaelle, §Architektur, Plattform und Accessibility]
- [x] CHK009 Ist die Normalisierung auf Entfernung eines UTF-8-BOM und Vereinheitlichung von CRLF oder CR auf LF ohne weitere Inhaltsaenderung genau begrenzt? / Is normalization precisely bounded to removing one UTF-8 BOM and converting line endings to LF without further content changes? [Clarity, Spec §Begriffe fuer den Einstieg, §Randfaelle]
- [x] CHK010 Ist eine offene Materialentscheidung mit `NeedsClarification`, stabiler Decision-ID, dem aus `BLOCKED` und `DO NOT RUN` gebildeten Stop-Marker und null ausfuehrbaren Invocations eindeutig definiert? / Is an open material decision unambiguously defined by `NeedsClarification`, a stable decision ID, the stop marker made from `BLOCKED` and `DO NOT RUN`, and zero executable invocations? [Clarity, Fail-Closed, Spec §FR-003, §SC-007]
- [x] CHK011 Ist fuer `ReadyForReview` eindeutig gefordert, dass Specify- und Autonomous-Prompt dasselbe exakte Ziel und dieselbe Authority-Grenze binden, ohne automatisch gestartet zu werden? / Does `ReadyForReview` clearly require both prompts to bind the same exact target and authority boundary without being started automatically? [Clarity, Prompt Authority, Spec §FR-004, User Story 3]

## Konsistenz der Bindungen / Binding Consistency

- [x] CHK012 Bleiben die erneuerten aktuellen Leaf-Bindungen ausschliesslich in `current-evidence-binding.json` aufgeloest, waehrend terminale und abgeschlossene Snapshots unveraenderte historische Evidence bleiben? / Are renewed current leaf bindings resolved only through `current-evidence-binding.json` while terminal and completed snapshots remain unchanged historical evidence? [Consistency, Spec §Aktuelle Bindung, §Klaerungen, §Annahmen und Abhaengigkeiten]
- [x] CHK013 Ist die genehmigte Reparatur konsistent auf Versionsreferenz, vier Receipt-/Review-Erneuerungen und Fortsetzung desselben Runs begrenzt, ohne neue fachliche Entscheidung oder Authority? / Is the approved repair consistently limited to the version reference, four Receipt and review renewals, and continuation of the same run without a new domain decision or authority? [Consistency, Evidence: binding-approval.md §Genehmigter Umfang und §Grenzen]
- [x] CHK014 Sind Einzelerzeugung und ausdruecklich genehmigte atomare Serie konsistent getrennt, einschliesslich Reihenfolge, Mitgliedschaft, Gesamtpublikation und Verbot einer Teilpublikation? / Are single creation and an explicitly approved atomic series consistently separated, including order, membership, all-or-nothing publication, and prohibition of partial publication? [Consistency, Spec §Scope, User Story 1, §Randfaelle]
- [x] CHK015 Bleiben Intake-Nicht-Autoritaet und separat gebundener Run-Delivery-Modus widerspruchsfrei: keine implizite Berechtigung aus Prompt, Review, Lifecycle oder historischer Delivery-Evidence? / Do intake non-authority and the separately bound run delivery mode remain consistent, with no implied permission from prompts, review, lifecycle, or historic delivery evidence? [Consistency, Authority, Spec §FR-004, §Autonomer Lauf, Evidence und Authority]
